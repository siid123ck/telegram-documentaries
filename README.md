# The Telegram Documentaries

A Telegram bot that, eventually, turns a user's portrait photo into a comedy
wildlife documentary *about them*: a hybrid animal portrait plus a short,
hushed, Attenborough-style voice note narrating "this magnificent specimen".

**Current status: Phase 3 — Interviewer (conversation engine + dossier), offline-verified.**
Once a photo passes the Bouncer, the bot interviews the subject. While the bot is
waiting for a photo, every text message still gets the fixed reply `hey mate!`. A
**photo** goes through the Bouncer, a Gemini vision check that decides whether a
human is in the picture:

- **Human photo** → the first interview question replaces the old `hey mate!`
  confirmation. The photo reference is stored only once that first question has
  been generated, so a failed start leaves nothing behind, and the chat moves to the
  interview.
- **Non-human photo** (cat, pizza, car, coffee mug, landscape, …) → a playful
  rejection names the object, e.g. *"Nice coffee mug — but this documentary needs a
  human. Send me a photo of a person."* Nothing is stored; the chat stays awaiting
  a photo.
- **Vision failure** (timeout, rate limit, outage, unreadable reply) → *"Vision's
  acting up — mind resending the photo?"*. Nothing is stored and nothing crashes.
- **Empty, oversized (over 10 MiB), or malformed photos** → a short nudge; the
  vision model is never called.
- **A photo mid-interview, or after the dossier is ready** → a nudge (the Bouncer
  is not called). After the dossier, send `/restart` for a new subject.

### The interview

- The bot asks **one question per message** and waits for your answer. Each question
  is generated by the model from your earlier answers.
- The interview runs for **5 to 7 questions**. From the 5th answer on, the model may
  finish; at the 7th answer the bot finishes regardless.
- A **blank** answer, or one over **1000 characters**, gets a short nudge and is not
  stored; the same question stays open. If the model fails while answering, the bot
  asks you to **resend your last answer**. Nothing is saved until the model replies,
  so resending is safe.
- When the interview finishes, the bot sends the **dossier as one text message**:
  three to seven quirks (topic and observation), then one suggested animal and a
  short reason. Nothing else is shown. The image, narration, and voice note come in
  later phases.
- **`/restart`** works in any phase and discards the photo, the answers, the
  question, and any dossier. The bot replies with the opening prompt. Other chats
  are not affected. If a model call is still running for your chat, `/restart` gets
  the one-at-a-time nudge instead and you can send it again in a moment.
- While a model call is running for your chat, any new message gets a short
  *"One at a time, please"* nudge and changes nothing.

Other messages (voice notes, stickers, edits, channel posts) are ignored without
crashing the process. Live Telegram and Gemini verification is **deferred** until
real credentials are supplied (see [Known limitations](#known-limitations)).

## What the bot does / pipeline

The intended product pipeline is a hub-and-spoke orchestrator with five stages:

```
Telegram update -> transport adapter -> orchestrator (state machine)
                                           -> Bouncer      (human?)
                                           -> Interviewer  (questions + dossier)
                                           -> Converter    (hybrid portrait)
                                           -> Scripter     (narration text)
                                           -> Narrator     (TTS voice note)
                                        -> Telegram send
```

So far the **gateway**, the **Bouncer**, and the **Interviewer** exist. The Bouncer
and the Interviewer are Google ADK agents behind a small seam each. The Interviewer
is the orchestrator: it owns the chat's phases `AWAITING_PHOTO → INTERVIEWING →
DOSSIER_READY` in a versioned, in-memory session keyed by chat. The Converter,
Scripter, and Narrator, and the `GENERATING` and `DELIVERING` phases, are deliberately
deferred to later phases (see
[Not supported / deliberately deferred](#not-supported--deliberately-deferred)).

## Prerequisites

- **Python 3.11+**
- **[`uv`](https://docs.astral.sh/uv/)** for dependency management (this project
  uses `uv 0.13.8`; any recent version works). `uv` is commonly installed at
  `~/.local/bin/uv`.

No manual `pip install` is needed — `uv sync` builds the locked environment.

## Setup

From the repository root:

```bash
uv sync                       # create .venv from the committed uv.lock
cp .env.example .env          # create your local config file
```

Then edit `.env` and fill in real values. The file (and its committed template
`.env.example`) has two keys:

| Variable | Purpose |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Bot token from [@BotFather](https://t.me/BotFather) (**requires credentials**). |
| `GEMINI_API_KEY` | Google AI API key used by the Bouncer vision gate and the Interviewer (**requires credentials**). |

> **Placeholder values fail fast by design.** `.env.example` ships markers such
> as `your_telegram_bot_token_here`. With those in place, the bot refuses to
> start: it prints **one** line naming the offending variable(s) and points at
> `.env.example`, then exits with status `2` — no stack trace, no partial boot,
> no secret values printed. This is a feature: a day-one failure must be a
> configuration failure, never a model failure.

`.env` is gitignored and is never committed. Secrets are read from the
environment only, are wrapped in `SecretStr`, and are never logged.

## Run locally (long polling)

```bash
uv run python -m telegram_documentaries
```

The bot uses **long polling** (`getUpdates`): no public URL, webhook, or inbound
HTTP server is needed. On startup it logs `polling started`, the package
version, and the config source (`file:.env` or `environment`) — never the values.
Send any text message before a photo and it replies `hey mate!`. Send a photo and
the Bouncer decides: a person starts the interview with the first question, anything
else gets the in-character rejection, and a vision failure asks you to resend. Answer
the questions one at a time; send `/restart` to begin again.
Press **Ctrl-C** to stop cleanly.

Without a real token (the current placeholder setup), the same command exits
immediately with the single fail-fast line described above — that is expected
until you supply real credentials. **Live-token verification is not performed
here because it requires credentials.**

## Developer scripts

`scripts/test` and `scripts/hooks` are the ground truth. Both resolve `uv`
robustly even if `~/.local/bin` is not on your `PATH`.

```bash
scripts/test     # verify: ruff check, ruff format --check, mypy, pytest
scripts/hooks    # auto-fix: ruff check --fix, ruff format, then mypy, pytest
```

Run `scripts/test` to check a change and `scripts/hooks` before committing. The
suite is fully offline: Telegram objects are faked at the boundary and both model
providers are scripted fakes, so no test contacts Telegram or Gemini, installs
packages, or reads your real `.env`.

## Pre-commit hooks

Install the git hooks once per clone:

```bash
uv run pre-commit install
```

Each commit then runs `ruff check --fix`, `ruff format`, `mypy`, `pytest`, and
[gitleaks](https://github.com/gitleaks/gitleaks) (hardcoded-secret detection).
The checks are whole-tree and cannot be silently skipped. To run them all
manually without committing:

```bash
uv run pre-commit run --all-files
```

The first install/run may download hook environments and the gitleaks binary,
so it needs network access once.

## Not supported / deliberately deferred

These are **out of scope** and will not work yet; they need a later spec:

- **Webhooks, public URLs, inbound HTTP servers** — transport is long polling only.
- **Persistence / restart survival** — session state is in memory only; a restart
  clears every chat's photo state.
- **The rest of the pipeline (Phases 4–7)** — no Converter, image generation,
  Scripter, Narrator/TTS, `GENERATING`, or `DELIVERING`. The dossier is delivered as
  text and goes no further.
- **Editing answers or the dossier** — there is no "go back" command, and a
  dossier cannot be regenerated. Use `/restart` to start over.
- **Authored `/start` behaviour** — `/start` is still delivered as plain text, so
  before a photo it gets `hey mate!`. Phase 7 owns its behaviour. During an
  interview it is recorded as an answer.
- Media groups: only the first valid photo is considered; caption text is ignored.
- Media, group administration, payments, rate limiting, localisation, and
  analytics are also out of scope by the project constitution.

## Known limitations

- **Live verification is deferred.** The offline suite covers the Bouncer, the
  photo gate, and the state store with faked vision. The real Telegram and Gemini
  paths (a coffee mug or landscape rejected in character, a person approved, a
  clean start and Ctrl-C) have **not** been run, because `.env` holds placeholder
  credentials only.
- **Deliberate change: the pass path is the first question, not `hey mate!`.** The
  Phase 2 confirmation is replaced on purpose (see
  `SPECS/2026-11-24-interviewer/requirements.md`).
- **Model-generated first question.** The first question comes from the model, so
  a passing photo waits on one model call. A transient provider error is retried
  once before the bot asks you to resend the photo.
- **One action at a time per chat.** A message that arrives while a photo or model
  call is still being handled gets a short "one at a time" nudge.
- **In memory only.** A restart clears every chat's interview.
- **Live Telegram and Gemini checks for Phase 3 are deferred.** The interview, the
  5-to-7 range, `/restart`, and the nudges are covered by the offline suite only.
- The Bouncer's free-form `reason` is logged but never shown to the user.
- Answers and model text are never logged. Logs record the chat id, phase
  changes, the question index, and the suggested animal's name only.
- Image bytes are always sent to the model as `image/jpeg`, since Telegram photo
  sizes are always JPEG.

See `SPECS/ROADMAP.md` for the phase plan and `SPECS/` for the full contracts and
validation checklist.
